## Целевой индивидуальный показ v3

Целевой `lct-2026-jury-v3` открывается без внешнего Basic Auth и без общих
аккаунтов. Каждый проверяющий создаёт отдельный синтетический аккаунт кандидата
или работодателя, задаёт собственный пароль и получает непрозрачный логин
`jury-…@example.invalid`. Старые seed-логины отключаются, их сессии отзываются.
Пароли БД, NAS/VPS, SSH-ключи и runner token остаются закрытыми.

Пятый override `compose.jury-individual.yaml` добавляется после публичного
override и включает `FSP_JURY_INDIVIDUAL_REGISTRATION=1`. Запишите этот флаг
в локальный `.env.jury`: обновлённый `scripts/jury-relay-nas.sh` тогда использует
все пять файлов для start/status/stop/validate. Без флага скрипт сохраняет
исходный закрытый режим с тремя файлами и Basic Auth. Другие значения флага
отклоняются. В индивидуальном режиме и `prepare`, и `start` требуют пройденного
gate; bootstrap-команда не обходит проверку внешнего доступа.

```bash
docker compose --project-name fspjury --env-file .env.jury \
  -f compose.yaml -f compose.jury.yaml -f compose.jury-relay.yaml \
  -f compose.jury-public-demo.yaml -f compose.jury-individual.yaml config --quiet
docker compose --project-name fspjury --env-file .env.jury \
  -f compose.yaml -f compose.jury.yaml -f compose.jury-relay.yaml \
  -f compose.jury-public-demo.yaml -f compose.jury-individual.yaml \
  up -d --no-deps --wait app edge
```

`config --quiet` не печатает развёрнутую конфигурацию с секретами. Перед
активацией проверяют, что compose-файл существует в целевом commit, миграции
применены, а новая версия app готова. TLS завершается на ru2, Caddy на NAS
слушает только loopback через relay и возвращает 404 для `/internal/*`.

Целевой предел — 200 jury-аккаунтов и пять регистраций в час на фактический
клиентский IP; вход ограничен десятью попытками в минуту на IP. Для освобождения
мест администратор использует только специально
проверенную адресную процедуру удаления/деактивации конкретных синтетических
аккаунтов и отзыва их сессий. Не применяют очистку volume, `down -v`, массовое
удаление таблиц или автоматический reset базы. Если штатная адресная команда
ещё не поставлена и не проверена, стенд закрывают для новых регистраций и
эскалируют оркестратору; данные вручную не удаляют.

Публичные `/legal/privacy` и `/legal/recommendations` доступны без сессии;
остальные ресурсы приложения требуют вход. Регистрация принимает только роль,
пароль 12–128 символов с подтверждением и явное согласие. Сервер назначает
синтетические имя/контакт, создаёт Secure/HttpOnly сессию на 8 часов и CSRF.
Почта, реальные email, ФСП mock, PDF-импорт и внешняя LLM отключены.

## Граница исходного закрытого стенда

- Compose-проект всегда называется `fspjury`. Он создаёт отдельные образы,
  PostgreSQL volume и volumes Caddy; прежние проекты `fsp`/`fspdelivery` и
  работающий `fspdelivery-app-1` не используются и не останавливаются.
- PostgreSQL и app не публикуют host-порты. Для выбранного relay внешняя точка — HTTPS nginx ru2; NAS Caddy доступен только на loopback TCP `18083`. LAN-порты `18083`/`18443` ниже относятся только к альтернативному прямому маршруту.
- Системный nginx NAS на 80/443, административные 8181/5443 и его конфигурация
  не изменяются. На роутере допустимы только правила WAN TCP 80 →
  `192.168.1.58:18083` и WAN TCP 443 → `192.168.1.58:18443`.
- Caddy 2.11.7 взят из официального образа и закреплён index digest
  `sha256:d8542f48d34a9cf4e4c11a478865229840e87e4c96ea3f439101f31a5d35f75f`.
  Сертификат получает Caddy напрямую по ACME; CDN и чужой TLS-терминатор не нужны.
- Access log Caddy не включён, чтобы не собирать IP посетителей без цели.
  Короткие runtime-логи нужны только для диагностики сертификата и состояния.
- На отдельной jury-сети Caddy получает фиксированный адрес `10.254.242.10`.
  Uvicorn доверяет `X-Forwarded-For` и forwarded scheme только от этого адреса:
  прямой контейнер или клиент не может подменить свой адрес таким заголовком.
  Если подсеть меняют через `FSP_JURY_SUBNET`, одновременно задают принадлежащий
  ей свободный `FSP_JURY_EDGE_IP`; доверие ко всей подсети или `*` запрещено.
- В исходном закрытом режиме `/internal/*` снаружи всегда отвечает 404. `/legal/privacy` и
  `/legal/recommendations` открыты до входа, чтобы показать фактического
  оператора и правила обработки. Все остальные пути сначала требуют отдельный
  Basic Auth, затем пароль готового синтетического аккаунта приложения.
- В исходном закрытом jury-режиме регистрация, вход по ссылке/коду, mock-почта, ФСП ID mock,
  загрузка резюме и внешний SMTP выключены. Используются только синтетические
  seed-данные; реальные данные вводить нельзя. Приложение запускается с
  `FSP_JURY_MODE=1`, secure-cookie и allowlist одного HTTPS origin.

## Подготовить закрытую конфигурацию

Команды выполняются в отдельной рабочей копии проекта на NAS. Они не меняют
роутер, DNS или системный nginx.

```bash
chmod +x scripts/jury.sh
./scripts/jury.sh init
./scripts/jury.sh config
./scripts/jury.sh validate
```

`init` интерактивно запрашивает фактическое имя и действительный публичный
email оператора, показывает их повторно и требует явное подтверждение
`OPERATOR-CONFIRMED`. Четыре независимых секрета создаются через
`secrets.token_urlsafe(48)`: пароль приложения, пароль Basic Auth, пароль БД и
runner token. Caddy формирует Argon2id hash локально. Пароли и hash записываются
только в игнорируемый Git `.env.jury` с `umask 077` и не выводятся скриптом.
Файл не перезаписывается автоматически. Администратор читает пароли только
локально из `.env.jury`. В исходном закрытом показе два пользовательских
пароля передавались отдельно; целевой индивидуальный v3 описан выше и не
публикует общий пользовательский пароль. После окончания оценки созданные
jury-аккаунты деактивируют адресной проверенной процедурой и отзывают сессии.

Для этого стенда подтверждены несекретные реквизиты: оператор данных —
`Колесников Никита Юрьевич`, публичный контакт — `inbox@nkolesnikov.ru`, страна
размещения и хранения — `RU`. Именно эти имя и email нужно ввести в `init` и
проверить на страницах политики. Инфраструктурные пароли и hash в документацию
не переносят. Историческое разрешение публикации общего seed-пароля не
распространяется на v3.

`./scripts/jury.sh config` проверяет env и Compose, затем показывает только
несекретные параметры. Нельзя запускать или сохранять полный вывод
`docker compose config`: в развёрнутой конфигурации находятся пароль БД,
runner token, пароль приложения и hash Basic Auth. Для автоматической проверки
используется только `docker compose config --quiet`, без `tee` и перенаправления.

## Gate альтернативного прямого маршрута

Владелец сети должен фактически подтвердить каждый пункт:

1. Выбран и отдельно проверен входящий маршрут. Текущий шлюз сообщает частный
   WAN `10.100.237.64`, поэтому исходящий адрес `46.8.231.30` нельзя помещать в
   DNS как адрес NAS без подтверждения провайдера. Для прямого варианта нужен
   выделенный глобальный IPv4 на текущем роутере либо управляемый внешний роутер
   с публичным адресом и явным пробросом до него. Адрес должен сохраняться на
   период оценки либо DNS должен своевременно обновляться.
2. В панели DNS A для `fsptest.kolesnikovny.ru` указывает на проверенную точку
   входа выбранного маршрута; лишней
   AAAA-записи, ведущей на недоступный IPv6, нет. NS и доступ к панели проверены.
3. NAS по-прежнему имеет зарезервированный DHCP/LAN `192.168.1.58`; TCP 18083
   и 18443 свободны. Никакие правила не направлены на 80/443 самого NAS.
4. Роутер пробрасывает только WAN TCP 80 → 192.168.1.58:18083 и WAN TCP 443 →
   192.168.1.58:18443. UPnP для проекта не используется. UDP 443 не требуется:
   HTTP/3 можно не публиковать.
5. Фаервол разрешает эти два TCP-направления. Проверка выполняется с другой
   сети, например мобильной, а не только из домашнего LAN.
6. Фактические имя/email оператора опубликованы на страницах политики и
   администратор зафиксировал `FSP_JURY_OPERATOR_CONFIRMED=1` после проверки.
   Подтверждённое владельцем размещение NAS в России отражено как
   `FSP_JURY_STORAGE_COUNTRY=RU`; это подтверждение владельца, а не вывод по
   GeoIP. Установлен срок удаления jury-volume после оценки.
7. В app включён jury-режим: `/api/health` сообщает `mode: jury-demo`, вход
   работает только паролем готовых аккаунтов, опасные публичные методы дают
   404. В репозитории нет `.env.jury` и самих паролей; полную развёрнутую
   Compose-конфигурацию не выводят, потому что она содержит секреты.
8. Проверена граница reverse proxy: два клиента через Caddy получают разные
   ключи ограничения входа, а прямой запрос к app с поддельным
   `X-Forwarded-For` не меняет фактический адрес клиента.

Для альтернативного прямого маршрута после подтверждения публичного WAN и проброса внесите подтверждённый адрес в `FSP_JURY_PUBLIC_IP`, задайте в
`.env.jury` ровно `FSP_JURY_ACTIVATE=DNS_AND_ROUTER_VERIFIED` и выполните:

```bash
./scripts/jury.sh gate
./scripts/jury.sh start
./scripts/jury.sh status
```

`gate` сверяет A-запись с указанным IPv4 и Compose-конфигурацию. Он не может
доказать проброс портов или статичность адреса, поэтому внешняя проверка нужна
отдельно. Caddy требует доступ CA к WAN 80 или 443; первый выпуск сертификата
может не состояться до корректного DNS и проброса.

## Выбранный relay через ru2

Из двух имеющихся серверов выбран менее загруженный `ru2`: IPv4 `80.87.198.60`,
hostname `inbox1.fvds.ru`, Ubuntu 24.04, свободно около 2,6 GiB RAM. `ru1` не
используется, потому что на нём уже работают несколько CRM. Эти сведения нужны
для выбора узла, но сами по себе не доказывают страну физического размещения.
Российский VPS выбран по поручению владельца; для промышленной эксплуатации сведения о физическом размещении подтверждают договором провайдера. VPS будет обрабатывать IP посетителей как
технический reverse proxy; страницы политики должны описывать этот маршрут.

Публичный путь:

```text
браузер → HTTPS nginx ru2 → 127.0.0.1:18470 ru2
        → зашифрованный reverse SSH → 127.0.0.1:18083 NAS
        → Caddy relay → app:8470
```

- Существующий nginx на VPS сохраняет глобальную конфигурацию и остальные
  vhost. Добавляется только exact vhost `fsptest.kolesnikovny.ru` из
  `docker/jury/nginx-vps.conf`; он проксирует только на loopback 18470.
- nginx перезаписывает полученный от клиента `X-Forwarded-For` своим
  `$remote_addr` и задаёт `X-Forwarded-Proto https`. Поэтому посетитель не может
  подменить адрес входным заголовком.
- На VPS отдельный SSH user `fspjury-tunnel` разрешает только remote forwarding
  и только listener `127.0.0.1:18470`. В `authorized_keys` одновременно нужны
  `restrict`, явное `port-forwarding` и `permitlisten="127.0.0.1:18470"`.
- На NAS Caddy публикуется только на `127.0.0.1:18083`, работает по HTTP и
  доверяет forwarded headers только bridge gateway `10.254.242.1`. Перед app он
  заново задаёт `X-Forwarded-For {client_ip}` и `X-Forwarded-Proto https`.
- Relay gate фиксирует default subnet `10.254.242.0/24` и адрес Caddy
  `10.254.242.10`; менять их без одновременного пересмотра trust boundary нельзя.
- Uvicorn по-прежнему доверяет только Caddy `10.254.242.10`. App сохраняет
  штатные `default` и изолированную `runner_net`; runner запускается с прежней
  VM-границей и бюджетами, чтобы задания по программированию оставались доступны.
- TLS завершается на VPS, а участок VPS–NAS шифрует SSH. При падении туннеля
  nginx получает ошибку loopback upstream и отвечает 502; обхода напрямую к app
  или Caddy по LAN/WAN нет.

Relay развёрнут назначенным оркестратором. Скрипты ниже описывают воспроизводимую подготовку и имеют отдельные проверки и изменяющие команды.

### Подготовка NAS без запуска

`./scripts/jury.sh init` создаёт `.env.jury` как описано выше. В этот локальный
игнорируемый файл добавляют только выбранный узел и пути к ключам вне Git:

```dotenv
FSP_JURY_VPS_HOST='80.87.198.60'
FSP_JURY_VPS_SSH_PORT='22'
FSP_JURY_TUNNEL_USER='fspjury-tunnel'
FSP_JURY_SSH_KEY_PATH='/Volume1/projects/Fsp-local/jury-relay/id_ed25519'
FSP_JURY_SSH_KNOWN_HOSTS_PATH='/Volume1/projects/Fsp-local/jury-relay/known_hosts'
FSP_JURY_RELAY_ACTIVATE=''
```

Создаётся отдельная Ed25519-пара только для туннеля. Private key остаётся на NAS
вне Git с режимом 0600 и владельцем UID 10001 контейнера; на VPS передаётся
только `.pub`. `known_hosts` заполняют
для `80.87.198.60`, а fingerprint Ed25519 сверяют через уже доверенный канал
управления `ru2`; одного `ssh-keyscan` без сверки недостаточно.

```bash
./scripts/jury-relay-nas.sh config
./scripts/jury-relay-nas.sh validate
```

### Точечная подготовка VPS

`scripts/jury-relay-vps.sh` закреплён за `80.87.198.60`. `preflight` только
читает состояние и отказывает, если домен уже объявлен другим vhost. Следующие
команды изменяют VPS и выполняются оркестратором по этапам:

```bash
./scripts/jury-relay-vps.sh preflight
./scripts/jury-relay-vps.sh install-ssh /secure/path/id_ed25519.pub
./scripts/jury-relay-vps.sh install-http
# После DNS A → 80.87.198.60 и внешней проверки HTTP challenge:
./scripts/jury-relay-vps.sh issue-cert
./scripts/jury-relay-vps.sh install-https
./scripts/jury-relay-vps.sh status
```

Для этого vhost access log выключен, а отдельный error log ограничен собственным
правилом logrotate: ротация при 1 MiB, семь архивов. Общие настройки и журналы
nginx не изменяются.

Для выпуска используется официальный Certbot 5.8.0, закреплённый index digest
`sha256:f70ad0adbb7e117f0fe42a63c553f28ea451edabc0148757b6efcd9735acaa20`,
с webroot только этого vhost. Существующий ACME account переиспользуется, а при
его отсутствии создаётся account без email: публичный адрес оператора не меняет
назначение на рекламные или CA-уведомления. `renew` повторяет webroot renewal и
перезагружает nginx только после `nginx -t`. Расписание renewal на VPS
проверяется отдельно. На выбранном ru2 уже включён certbot.timer с Certbot 5.6.0 и reload nginx; его настройки сохранены. Webroot в контейнере и на VPS одинаков: /var/www/fsptest-acme. Успешный reconfigure проверил staging-продление и сохранил этот путь; ручная команда renew ограничена только сертификатом данного домена.

### Активация relay

До изменения DNS приватный путь поднимают отдельной командой; edge NAS при этом
доступен только на loopback, а HTTP bootstrap VPS отвечает 503:

```bash
./scripts/jury-relay-nas.sh prepare
```

После этого оркестратор проверяет на VPS listener `127.0.0.1:18470`, health через
туннель и работающий runner. Только после подтверждения страны VPS, SSH
fingerprint, DNS, сертификата, loopback listener и внешних тестов задают ровно
`FSP_JURY_RELAY_ACTIVATE=VPS_TLS_AND_TUNNEL_VERIFIED`, затем:

```bash
./scripts/jury-relay-nas.sh gate
./scripts/jury-relay-nas.sh start
./scripts/jury-relay-nas.sh status
```

Из внешней сети повторяют все проверки раздела «Приёмка», отдельно проверяют
два разных client IP в rate limit, поддельный входной `X-Forwarded-For`, 404 для
`/internal` и fail-closed 502 при контролируемой остановке только tunnel.
Флаг `FSP_JURY_INDIVIDUAL_REGISTRATION=1` должен быть установлен до запуска;
при его отсутствии будет выбран закрытый режим. Публичный запуск до этих проверок не заявляется. Если relay не будет готов к
сроку, резерв остаётся прежним: видео и воспроизводимая локальная инструкция.

## Приёмка индивидуального v3

До публикации тега проверяют из внешней сети и фиксируют commit, время и
результаты в новом протоколе:

1. `GET /legal/privacy` и `/legal/recommendations` возвращают 200 без входа;
   продуктовые ресурсы требуют сессию, Basic Auth не появляется.
2. Регистрация кандидата и работодателя принимает пароль 12–128 символов,
   совпадающее подтверждение и `consent=true`; иные роли, отсутствие согласия,
   короткий/длинный пароль отклоняются.
3. Ответ выдаёт только серверный `jury-…@example.invalid`, синтетические defaults,
   Secure/HttpOnly cookie на 8 часов и CSRF. Реальный email отправить нельзя.
4. После logout сохранённый логин и пароль снова входят, а неверный пароль нет.
   Старые seed-пароли и сессии v2 не работают.
5. Срабатывают 5 регистраций в час на реальный IP и общий предел 200 аккаунтов;
   поддельный `X-Forwarded-For` не обходит лимит.
6. Email-flow, mock-mail, resume import, ФСП mock, Google/Apple OAuth,
   `/internal/*`, БД, Docker API, NAS admin и runner недоступны снаружи.
7. VM-задача проходит через фактический runner; LLM остаётся выключенной.
8. Адресная деактивация одного тестового jury-аккаунта отзывает только его
   сессии и освобождает ровно одно место, не затрагивая остальных.

V3 активирован; перечисленные browser/HTTPS-пункты пройдены. Проверка ограничена
указанными сценариями и не является полным pentest или нагрузочным испытанием.

## Приёмка исходного закрытого показа с внешней сети

Не помещайте пароли в историю shell или диагностические файлы. Введите их в
браузере и проверьте DevTools либо используйте интерактивные переменные shell.

```bash
read -r -p 'Basic user: ' JURY_USER
read -r -s -p 'Basic password: ' JURY_EDGE_PASSWORD; printf '\n'
curl -fsS https://fsptest.kolesnikovny.ru/legal/privacy >/dev/null
curl -sS -o /dev/null -w '%{http_code}\n' https://fsptest.kolesnikovny.ru/
curl -fsS -u "$JURY_USER:$JURY_EDGE_PASSWORD" https://fsptest.kolesnikovny.ru/api/health
curl -sS -u "$JURY_USER:$JURY_EDGE_PASSWORD" -o /dev/null -w '%{http_code}\n' https://fsptest.kolesnikovny.ru/internal/runner/claim
unset JURY_EDGE_PASSWORD
```

Ожидается: legal policy — 200 без Basic Auth; `/` без Basic Auth — 401;
health с Basic Auth — 200 и `jury-demo`; `/internal/...` — 404 даже с паролем.
Далее в браузере проверить password-only вход кандидата и работодателя,
отсутствие регистрации/почты/ФСП ID/загрузки резюме, secure session cookie,
изменяющий запрос с корректным CSRF и такой же запрос без CSRF (403). Проверить
основной сквозной сценарий на синтетических данных и выход из сессии.

Не заявляйте стенд доступным, пока HTTPS и эти проверки не пройдены из внешней
сети. Для выбранного relay на период оценки контролируйте `./scripts/jury-relay-nas.sh status` и ограниченный
`./scripts/jury-relay-nas.sh logs`; не включайте access log. Остановка сохраняет данные:

```bash
./scripts/jury-relay-nas.sh stop
```

После согласованного срока хранения удаление только отдельного jury-контура
выполняется явно: `./scripts/jury-relay-nas.sh reset --yes`. Команда удаляет контейнеры,
сети и volumes проекта `fspjury`; `.env.jury` удаляется вручную после проверки,
что он больше не нужен. Это действие только для окончательного вывода стенда
из эксплуатации, а не для освобождения лимита аккаунтов; автоматически его не
запускают. Прежние NAS-проекты команда не затрагивает.

Источники настройки Caddy: [Automatic HTTPS](https://caddyserver.com/docs/automatic-https),
[Basic Auth](https://caddyserver.com/docs/caddyfile/directives/basic_auth) и
[официальный Docker image](https://hub.docker.com/_/caddy).
